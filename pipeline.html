Context

The COEQWAL stack is described in coeqwal_project_ecosystem.md — a Next.js 15 static-export website, a FastAPI backend at api.coeqwal.org, and a PostgreSQL data platform feeding it. This document covers a narrower question: how individual brief pages (theme, LOI, strategy) are produced and published.

Briefs are version-locked editorial artifacts. Once a brief version is published, its content does not change — even if the backend data does. A new version is cut explicitly, by the team, when the team decides one is needed.

Pipeline

What each box does

api.coeqwal.org — the single source of truth for all COEQWAL data. Documented at /docs (OpenAPI). Briefs read from it once at publish time, never at view time.

Python build step (publish-time). When a new brief version is cut, the build step:

  • fetches the scenarios, LOIs, sector tier results, and statistics the brief needs from the API
  • renders the brief's figures as inline SVG
  • fills the brief's HTML template with values and figures
  • writes a JSON sidecar capturing every value used in the brief and the scenario IDs — the sidecar is the audit record. Its provenance record differs by brief family (corrected 2026-07-30): - Cache-backed briefs (location, baselines): the sidecar's data_sources records, per API response used, the endpoint called, its fetch timestamp, and a SHA-256 hash of the cached payload bytes (sidecar.py). - Scenario-results briefs: the data file records provenance as the snapshot label the set was built from — 2026-08-01 for the committed set; this line said 2026-07-02 until 2026-08-02 — plus an API version string (api.coeqwal.org v2.1.1, results.py). It does not list endpoints or a per-response timestamp, because these briefs read the locked snapshot, not the live API.
  • outputs the brief HTML + JSON to builder/output/ (cache-backed dev briefs) or the coeqwal-briefs repository root (scenario-results set) — see "Where the brief lives" and "Versioning" for the filenames; nothing is written into the website repo

Static brief (published artifact). A fully self-contained HTML file: text, figures, and styles inline. Served by the website with no server-side rendering and no runtime API calls. Works offline. Prints to PDF cleanly. Frozen until the next version is cut.

Live explorer (runtime). The interactive surface on the main site. Queries api.coeqwal.org on demand. Not produced by this pipeline; included in the diagram because briefs link into it.

§9 hand-off (user navigation). Each brief's §9 "Explore further" link is a deep link into the live explorer, pre-configured with the brief's scenario context. This is how a reader transitions from a frozen reference to live exploration.

Where the brief lives in the website repo

The Python build step writes the brief HTML and JSON sidecar into the website repo as static assets. Likely path TBD with the web team. Candidate: apps/main/public/briefs/{brief-id}_v{N}.{html,json}. Next.js serves them as static files; no rendering happens at site build time.

(Superseded 2026-07-30 against builder/build.py.) No code writes outside the coeqwal-briefs repository. The build step has exactly two output destinations: builder/output/ for the cache-backed dev briefs (OUTPUT_DIR), and the coeqwal-briefs repository root for the published scenario-results set (RESULTS_OUTPUT_DIR, build.py:62; overridable per run with --out). There is no write into the website repository and no apps/main/public/briefs/ path on disk. How the website ultimately serves a published brief is a separate, still-open question with the web team (see Open items); it is not something this build step does today.

Versioning

  • Brief files are named {brief-id}_v{N}.html. Version increments only when the team cuts a new version. (Superseded 2026-07-30 against builder/.) No code produces the {brief-id}_v{N} pattern. The actual filenames are: - Location and baselines briefs: {brief_id}_dev.html and {brief_id}_dev.json, with the version recorded in the sidecar as the literal string dev (compute.py, baselines.py, sidecar.py). - Scenario-results briefs: scenario_results_brief_<slug>_prototype_v0_3.html for the HTML and scenario_results_brief_<slug>_v0_3.json — the same name without prototype_ — for the data file (results.py, VERSION = "v0_3"). - Renaming files toward the documented {brief-id}_v{N} pattern would disable verification: the rendered-HTML and sidecar checks look the _dev and scenario_results_brief_… names up by name, so a renamed file reads as "not built."
  • The unversioned URL (e.g. /briefs/baselines) points to the highest published version.
  • Old versions remain reachable at their versioned URL — public, citable, frozen.
  • If backend data changes (a tier result is revised, a scenario updated), affected briefs are flagged for review but do not auto-update.

Anchors and the address space

In-brief anchor identifiers are settled independently of the published address scheme. A brief's section anchors are properties of its own content: they are fixed when the version is cut and travel inside the frozen artifact. The path a brief is served from is a property of the site's URL space and is set outside the brief. Neither constrains the other. Whatever the published address scheme is, no brief's anchors change with it, and no decision about the address space is an edit to brief content.

The practical consequence is that addressing and content can be settled on different clocks: a decision about the address space taken after a brief's content is frozen does not reopen the brief.

What is not in this pipeline

  • Live data in the brief. Briefs never call the API at view time. If a value needs to be live, it belongs in the explorer.
  • Per-user customization. Briefs are the same for every reader.
  • Personalization, filters, interactivity. Those live in the explorer.

Development builds

Rewritten 2026-07-18. The earlier version of this section described the pre-builder prototype phase — brief HTML authored by hand, with values read from MATLAB and typed in directly. That phase ended when the builder came online (2026-06-06), and MATLAB is no longer part of the brief workflow in development or production.

Brief development uses the same pipeline as production publishing. Dev briefs are built with build.py fetch | render | verify in the coeqwal-briefs repo, reading from the cached 2026-07-02 API snapshot — the locked source of record (see "Data evolution and the lock"). Every value in a dev brief traces to a cached API payload through the same verification stage a published brief will use; the only difference between a dev build and a published one is that dev outputs (builder/output/*_dev.html) are unversioned working files, not version-locked artifacts. The invariant is unchanged in both cases: data is fetched from the API once at build time, never at view time.

There are two separate data roots, and different briefs read different ones.

  • builder/cache/ — a directory keyed by API endpoint (briefbuilder/client.py, DEFAULT_CACHE_DIR). The location-of-interest briefs (folsom-loi, oroville-loi, shasta-loi, trinity-lewiston-loi, yuba-marysville-loi, and salt-slough-loi, added 2026-07-31) read from here. (Corrected 2026-08-02: this bullet listed five location briefs and named the baselines brief as a reader of the cache. Since the 2026-08-01 wiring the baselines brief takes its numbers from the snapshot; only its scenario list still comes from the cache.) build.py fetch is the only thing that writes it: it opens the network to api.coeqwal.org, and with refresh=True it overwrites each endpoint's cache entry with the exact bytes returned. Every location and baselines sidecar records a SHA-256 hash of those exact cached bytes (canonical-JSON payload hash, briefbuilder/sidecar.py), so the audit record is pinned to the cache the build read.
  • builder/snapshots/<date>/ — the dated dataset snapshots. The 23 scenario-results briefs and the baselines brief read from here (see "The scenario-results family" below). No build ever writes these directories; they are committed, fixed inputs, and build.py fetch --brief results refuses to run against them. build.py defaults to the most recent snapshot and --snapshot DIR names another; the committed set was built from 2026-08-01. (Corrected 2026-08-02: this bullet named a single locked builder/snapshots/2026-07-02/.)

So fetch populates the cache, not the snapshot, and it touches only the location briefs. fetch is held and must not be run (standing note in builder/RUNNING.md, narrowed 2026-08-02 to cover fetch alone and to end at the 2026-08-07 content freeze): running it would overwrite the committed cache with live API bytes and invalidate the SHA-256 hashes the six location sidecars record. (Corrected 2026-08-02: the reason given here was that the 2026-07-29 drift was unresolved. That question is settled — all 31,390 per-location values are identical across the 2026-07-02, 2026-07-31 and 2026-08-01 snapshots. The hold now rests on not rewriting a published audit trail for values that have not moved.)

Dev outputs for the cache-backed briefs (builder/output/*_dev.html + *_dev.json) are unversioned working files, not version-locked artifacts. The invariant is unchanged for both roots: a brief's data is fixed at build time — from the cache or from the snapshot — and never fetched at view time.

It was prototype-figure material only and was never an input to this pipeline; it is fully retired now that tier_continuous is served by the API. Kept here so figures from that era can be traced to their source.

The scenario-results family (added 2026-07-30)

This family is now most of the pipeline — 23 briefs, one per strategy — and the rest of this document, written before it existed, does not otherwise describe it. It is built as a set through builder/briefbuilder/results.py, kind results, and differs from the cache-backed briefs in every respect below:

  • Input is a dated snapshot under builder/snapshots/, never the live API. build.py defaults to the most recent and --snapshot DIR names another; the committed set was built from — and states — 2026-08-01. (Corrected 2026-08-02: this named a locked 2026-07-02 snapshot via results.DEFAULT_SNAPSHOT. That constant survives only in the legacy shim, which now refuses to run without a named snapshot rather than falling back to it.) build.py fetch --brief results refuses and exits 2 rather than opening a connection, so the set cannot silently pick up live data; to look for drift, run python3 api_watch.py check instead.
  • The strategy roster is read at build time from projects/coeqwal-briefs/_meta/COEQWAL_Strategy_Naming_Proposal.html, by matching its HTML table (results.parse_naming_table, which expects 24 rows). This makes that editorial file a live build input: its HTML table structure must not change, or the parse breaks. Note there are two directories named _meta/ in this tree — one at the COEQWAL root and one inside coeqwal-briefs; the file the build reads is the one inside coeqwal-briefs (confirmed against results.py: NAMING_PATH = REPO_ROOT/_meta/… where REPO_ROOT is the coeqwal-briefs repository root). Do not confuse it with the root _meta/.
  • Output lands at the coeqwal-briefs repository root, not in builder/output/ (RESULTS_OUTPUT_DIR). The set is a publication artifact of 46 files (23 HTML + 23 JSON), staged by filename and paired one-to-one by slug with strategy-briefs/; keeping them at the root is deliberate, and renaming them would orphan the committed set (see "Versioning" for the filename scheme).
  • Strategy 4.2 is absent from the snapshot and is skipped and logged, never imputed — which is why the set is 23 briefs, not 24.
  • Three flags apply to this kind only (ignored by the others): --strategy (repeatable; a slug or public id such as 4.2, selecting a subset), --checked-at (pins the verification timestamp; defaults to the current time in UTC), and --out (output directory for scratch builds; defaults to the repository root where the published set lives).

The 2026-08-01 rebuild (added 2026-08-02)

The pipeline was rebuilt on 2026-08-01 and the whole published set re-rendered and committed. Everything above this section that predates it has been corrected in place; this section records what changed, because the changes are not visible from the file layout alone.

Aggregation moved into COEQWAL. An area value used to be the served weighted_score field from the tiers endpoint. It is now the unweighted mean of that area's per-location tier values, computed here from the snapshot. The reason is measurable: between 2026-07-02 and 2026-07-31 the 31,390 per-location values were identical while the served weighted_score changed in 465 of 575 cells and crossed a tier band in 176. The whole of that drift lived in the derived aggregate. Under local aggregation the episode would not have reached a brief.

One threshold became two (builder/briefbuilder/tierscale.py). DEAD = 0.05 was removed rather than aliased, so every call site had to be read and assigned:

  • MOVEMENT = 0.10 — a claim. Below this a difference is not reported as movement, at every grain.
  • DETECTION = 0.05 — not a claim. The floor for counting a location as differing at all, so a count can be reported. A difference at this floor is not a change in result, and reader-facing wording must not say it is.

Printed precision is one decimal, floored, never rounded, so a printed value always sits inside the band its own label names and 5.0 is unreachable by construction.

Three of the four brief kinds now read the snapshot at first hand — the 23 results briefs, the baselines brief, and (for its scenario list only) the location set. The sector brief is not yet wired and remains the last violation of "every brief reads the same source at first hand".

Seven modules were added. source.py, tierscale.py, naming.py, assemble.py, decompose.py, verifier.py, acceptance.py. Which of them a build actually reaches is documented, with an import trace, in builder/README.md — and the answer is not all of them.

Which document is authoritative (settled 2026-08-02)

builder/README.md calls this document the canonical design, while this document defers to measured builder behaviour. That was a loop, and neither file could be believed on the strength of the other. It resolves by subject rather than by precedence:

  • This document is authoritative for the editorial and publishing design — what a brief is, version-locking, the address space, versioning, where a published brief lives, and what is deliberately out of scope. A disagreement about intent is settled here.
  • The code is authoritative for what the builder does — data roots, defaults, flags, filenames, thresholds, which module runs. builder/README.md and builder/RUNNING.md are descriptions of the code, kept current against it; where one of them and the code disagree, the code wins and the document is the defect.
  • Where this document describes builder behaviour, it is a description too, and the same rule applies to it. Every such statement in this file has been checked against the source as of 2026-08-02; a statement here that the code contradicts is a finding, not a requirement on the code.

Data evolution and the lock (added 2026-06-10; lock declared 2026-07-02)

The API's data changed while the platform team finished their work (examples from the 2026-06-10 audit: salmon abundance went from unserved to served; the community-water-systems location count moved from 124 to 75). The lock was originally estimated for early August 2026; on 2026-07-02 the dataset was declared essentially locked — the 2026-07-02 snapshot is the source of record, and the CWS location count settled at 74 (one strategy-specific exception under review with the data team). Launch is September 3. The discipline below stays in force for catching any residual drift:

  • Builds compare against dated snapshots, never against "the API." builder/api_watch.py snapshot saves the full API state (every scenario's tier and location data, plus the scenario and indicator lists) to builder/snapshots/YYYY-MM-DD/ with a comparable fingerprint; api_watch.py check reports drift between the live API and the latest snapshot; api_watch.py diff compares two snapshots. Snapshots are committed, so the drift history lives in the repo. A weekly automated check reports drift; a manual check before any build session is cheap. (Superseded 2026-07-30.) There is no scheduler anywhere in the repo: api_watch.py check is run by hand. The script's own text treats a scheduled run as hypothetical — it names a weekly cadence as intended discipline, and its exit code is shaped so it could drive a cron or scheduled task that notifies on drift, but none is configured. A manual check before any build session is cheap; because that manual check is the only safeguard, the 2026-07-29 API change went roughly four weeks undetected.
  • At the lock, one final snapshot is taken and labeled; from then through launch, all brief builds read from that snapshot only, making every build reproducible against a fixed reference.
  • Scheduling flag — resolved by the early lock (2026-07-02): the concern was that the brief timeline's content freeze (August 7, 2026; earlier drafts of this document said July 29 — corrected 2026-07-30 against COEQWAL_current_state.html) preceded an early-August lock. With the dataset essentially locked on July 2, builds against the 2026-07-02 snapshot precede the freeze comfortably; only the formal final verification pass (and a re-render if any residual change lands) remains to schedule before September 3.
